# Bitfinex 綠葉放貸機器人 🍃

自動化 Bitfinex funding(放貸)掛單,部署在 GitHub Actions 上長期免費執行。
每個工作長跑約 5.7 小時、每 60 秒依市場實際成交價檢查並調整掛單一次。

**流動性紅線:任何掛單天期都不超過 7 天**(程式寫死,設定檔也改不掉),在這個前提下追求最高年化。

---

# 掛單策略

## 一、每輪執行流程

長跑模式下每 60 秒做一遍(單次模式只做一遍):

1. **讀市場**:抓全市場最近 4 小時的實際成交,分別整理 **2 天期**與 **7 天期**兩個市場的成交利率分布
2. **調整舊掛單**:每筆掛單依「已經掛了多久」算出目標價(越久越低),目前利率偏高超過 2% 就撤單重掛,新單繼承舊單的年齡
3. **處理零頭**:可用餘額不足最小掛單額(150)但還有掛單時,撤回最新的一筆,把零頭併進去一起重掛
4. **掛新資金**:可用餘額 − `reserve_amount`,拆成多筆(見「三」),每筆在兩個市場中挑**目標價較高的**掛出
5. **決定天期**:7 天期市場成交的就是 7 天;2 天期的單只有利率達到「近一週尖峰」才鎖滿 7 天,否則 2 天

任一幣別失敗會以非零狀態碼結束,GitHub Actions 顯示紅燈,錯誤內容也會進儀表板。

## 二、為什麼這樣定價 —— 來自半年實跑與兩年回測

### 舊版實際表現:成交利率 7~9%,實現年化只有 5.2%

2026-08-21 ~ 09-21 的真實帳務(`history/`):成交加權日利率 0.0205%(年化 7.5%),
但以錢包餘額算的實現年化只有 **5.2%**。差距全是資金閒置:

| 時間去哪了 | 佔比 | 原因 |
|---|---|---|
| 放貸中生息 | 66% | — |
| 掛單等成交 | 6% | 正常代價 |
| **完全沒掛單** | **27%** | 見下 |

沒掛單的 27% 有三個來源,新版各有對策:

| 來源 | 證據 | 對策 |
|---|---|---|
| GitHub 排程 `*/15` 實際上**每 4 小時才跑一次**(中位 231 分鐘) | 近 50 次執行的間隔 102~413 分鐘;放貸回流到下一筆掛單中位數 2 小時 | 改成**長跑模式**:每個工作跑 340 分鐘、每 60 秒檢查一次,不再依賴排程準時 |
| 近 50 次執行有 **30 次掛單失敗** | `Invalid offer: not enough USD balance`:等分金額的浮點尾差讓最後一筆略大於餘額,之後的單全沒掛 | 金額一律無條件捨去到 0.01 |
| 部分成交留下 **< 150 的零頭**,永遠掛不出去 | 例:掛 155.9 成交 30.5,剩 125.4 閒置到下一筆回流 | 零頭併單:撤回最新一筆掛單一起重掛 |

### 7 天期市場比 2 天期貴 15~70%

Bitfinex 的 funding 成交是依天期分市場的。同一時刻,借 7 天的人付的利率系統性高於借 2 天的:

| 月份 | 2 天期成交中位 | 7 天期成交中位 | 倍數 |
|---|---|---|---|
| 2026-05 | 0.0125% | 0.0210% | 1.67 |
| 2026-06 | 0.0131% | 0.0199% | 1.52 |
| 2026-07 | 0.0180% | 0.0248% | 1.38 |
| 2026-08 | 0.0155% | 0.0219% | 1.41 |
| 2026-09 | 0.0150% | 0.0222% | 1.48 |
| 2026-10 | 0.0140% | 0.0161% | 1.15 |

(近兩年每個月都是 7 天期較高,倍數 1.1~3.3)。7 天期市場較薄 —— 近一年約 53% 的 15 分鐘窗口有成交 ——
所以不是永遠掛 7 天,而是**兩個市場同時看,哪邊目標價高就掛哪邊**;7 天期沒成交紀錄時自然退回 2 天期。

借方可以提前還款(2 天期放貸實際持有時間中位數只有 5 小時,37% 撐滿兩天),所以 7 天只是**上限**,
不是保證鎖 7 天;但反過來說資金最慢 7 天一定回來,這就是流動性紅線的意義。

### 依年齡遞減定價,而不是固定階梯

舊版把階梯固定鋪在成交帶 25~90 分位、30 分鐘沒成交就砍掉重掛。新版每筆掛單剛送出時掛在近 4 小時成交的
**第 90 分位**(只被尖峰買家吃到),之後隨時間線性往下走,**240 分鐘**降到**第 40 分位**(幾乎必定成交)。
行情好時高價先成交,行情差時自動讓價,不需要人工判斷「現在該貪還是該讓」。

### FRR 仍然不可用

ticker 的 FRR 是「已提供資金」的加權平均,含過去鎖進去的長天期高利單。近一年 FRR 中位 0.031~0.047%,
而 2 天期成交中位只有 0.010~0.020%(FRR 的 0.4 倍),7 天期也只有 FRR 的 0.4~0.9 倍。
掛在 FRR 幾乎不會成交;**追求「年化維持在 FRR 之上」是結構性做不到的**。

### 回測:兩年、同一套模型下的比較

`py backtest.py` 用 fUSD 2 天期與 7 天期的 15 分鐘 K 線(2024-09 → 2026-10)重播,
成交條件是「該市場該 15 分鐘的最高成交價 ≥ 掛單利率」,借方持有時間依 `history/` 實際分布抽樣:

| 策略 | 機器人每幾分鐘行動 | 放貸中 | 等成交 | 成交加權利率 | **實現年化** |
|---|---|---|---|---|---|
| 舊版(2 天期階梯) | 240(舊排程實況) | 75% | 18% | 0.0201% | 5.7% |
| 舊版(2 天期階梯) | 15 | 85% | 15% | 0.0185% | 5.8% |
| **新版(雙市場遞減)** | 240 | 88% | 7% | 0.0224% | 7.6% |
| **新版(雙市場遞減)** | **15(長跑模式)** | **95%** | **5%** | **0.0224%** | **8.5%** |

舊版模型值 5.7% 對上真實 5.2%,模型略偏樂觀(沒算 API 失敗與排隊優先權),所以看相對差距:約 **+45%**。
參數掃描(起始分位 75~99、最低分位 30~50、遞減 120~720 分鐘)結果都在 8.4~8.8% 之間,預設值落在平坦的高原上,
不是過度擬合的尖點。其他結論:成交帶回看 4 小時優於 24 小時(等待時間少一半);尖峰鎖倉比完全不鎖多約 0.7 個百分點;
只用 2 天期市場約 8.2%,只用 7 天期約 8.2%,兩者取優 8.5%。

## 三、金額怎麼拆 —— 隨餘額自動調整

```
n = min(num_ladder_steps, 可用資金 ÷ min_offer_size)   ← 每筆不低於交易所最小額
n = max(n, ⌈可用資金 ÷ max_offer_size⌉)                ← 每筆不超過單筆上限
n = max(1, min(n, 可用資金 ÷ min_offer_size))          ← 防呆:上限誤設過小時仍守住最小額
每筆金額 = ⌊可用資金 ÷ n⌋(無條件捨去到 0.01)
```

| 可用餘額 | 拆成 | 每筆金額 |
|---|---|---|
| 100 | 不掛單 | 低於交易所最小額 150 |
| 160 | 1 筆 | 160 |
| 623 | 4 筆 | 155.75 × 4 |
| 6,000 | 4 筆 | 1,500 × 4 |
| 25,000 | 5 筆 | 5,000 × 5 |
| 120,000 | 24 筆 | 5,000 × 24 |

每筆獨立挑市場、獨立遞減,所以多筆資金會自然分散在不同價位與天期;想拉開更多可以設 `rung_spread_percentile`。

## 四、天期:最長 7 天

| 情況 | 天期 |
|---|---|
| 依 7 天期市場定價成交 | 7 天 |
| 依 2 天期市場定價,利率 ≥ 近一週 2 天期收盤價第 `spike_percentile`(90)分位 | `max_period_days`(7)天 —— 尖峰鎖住,回測顯示尖峰後 30 天的平均利率只有尖峰時的一半 |
| 依 2 天期市場定價,一般行情 | 2 天 |

`MAX_PERIOD_DAYS = 7` 寫在 `bot.py` 裡,`max_period_days` 設更大會被壓回 7,送單前還有最後一道 `clamp_period` 檢查。
放貸一旦成交就不能提前收回,所以這條紅線保證任何時候**資金最慢 7 天全部回到錢包**。

## 五、必須關掉 Bitfinex 原生自動放貸

交易所內建的 Auto-Renew 會用「rate 0(跟隨 FRR)」把整筆餘額掛出,和機器人搶同一筆錢:
機器人把它當過時舊單取消、改掛自己的價,兩套系統互相拆台,資金大量空轉。

本專案已透過 API 關閉(`auth/w/funding/auto`, status=0)。若要重新確認:
掛單紀錄裡不再出現「利率 0.0000%/日」的整筆大額掛單,就表示關乾淨了。

# 設定檔 config.json

所有利率單位都是**每日利率 %**(0.02 = 0.02%/日 ≈ 年化 7.3%)。

| 欄位 | 預設 | 說明 |
|---|---|---|
| `paused` | — | **暫停掛單**(全域)。true = 收回所有未成交掛單、不再掛新單 |
| `loop_interval_seconds` | 60 | 長跑模式每幾秒檢查一次 |
| `publish_every_minutes` | 15 | 長跑模式每幾分鐘發佈一次儀表板、重新讀取 config.json |
| `enabled` | — | 是否啟用該幣別(內建 USD、UST,可自行新增) |
| `min_offer_size` | 150 | 最小掛單金額(Bitfinex 規定 USD/UST 最少 150) |
| `max_offer_size` | 5000 | 單筆掛單上限,資金多時自動拆更多筆 |
| `num_ladder_steps` | 4 | 最多拆成幾筆 |
| `rung_spread_percentile` | 0 | 每多一筆,起始分位往上加幾分位(0 = 各筆同價) |
| `markets` | [2, 7] | 定價參考哪幾個天期的成交市場(> 7 會被壓回 7) |
| `band_hours` | 4 | 成交帶回看幾小時 |
| `start_percentile` | 90 | 新掛單掛在成交帶第幾分位 |
| `floor_percentile` | 40 | 遞減到的最低分位 |
| `decay_minutes` | 240 | 幾分鐘從起始分位降到最低分位(0 = 不遞減) |
| `reprice_tolerance_pct` | 2 | 目前利率比目標高超過幾 % 才撤單重掛(避免為了零點幾 % 一直換單) |
| `min_daily_rate_pct` | 0.01 | 利率地板,目標價不低於此 |
| `max_period_days` | 7 | 天期上限,**程式硬性 ≤ 7** |
| `spike_percentile` | 90 | 2 天期單利率達近一週收盤第幾分位就鎖滿天期(100 = 不鎖) |
| `spike_lookback_hours` | 168 | 尖峰門檻回看幾小時 |
| `consolidate_dust` | true | 零頭不足最小額時撤回最新掛單併入 |
| `max_lend_amount` | 0 | **最大放貸總額**(生息中 + 掛單中),達到就停止新增。0 = 不限 |
| `reserve_amount` | 0 | 保留在錢包不掛出的金額 |

## 想調整策略時

| 目標 | 怎麼做 |
|---|---|
| 更快成交、減少等待 | `start_percentile` 調低(如 75)、`decay_minutes` 調短(如 120) |
| 更貪心等高利率 | `start_percentile` 調高(如 95)、`floor_percentile` 調高(如 50)、`decay_minutes` 拉長 |
| 資金一定要 2 天內回來 | `max_period_days` 設 2、`markets` 設 `[2]`(年化約少 1~2 個百分點) |
| 拒絕低利率行情 | `min_daily_rate_pct` 調高(過高會大量空轉) |
| 限制總投入金額 | `max_lend_amount`(例如只想放 3000,其餘留在錢包) |
| 留一筆錢不放貸 | `reserve_amount` |
| 加開幣別 | 把 `UST` 的 `enabled` 改 `true`,或依相同格式新增 |

改完可以先跑 `py backtest.py` 看兩年回測的影響(見「本機測試」)。

## 暫停與恢復

`config.json` 最上層的 `paused` 控制全域暫停(也可在個別幣別裡設 `"paused": true` 只停該幣別):

```json
{ "paused": true, ... }
```

暫停時機器人每輪只做兩件事:**收回所有未成交的掛單**,然後停手不掛新單。
儀表板照常更新,執行 log 會顯示 `⏸ 掛單已暫停`。長跑中的工作每 15 分鐘重讀 `config.json`,
所以 commit 後最多 15 分鐘生效,不必等工作結束。

**已經成交的放貸無法提前收回** —— 但天期上限 7 天,所以暫停後最慢一週資金全部回到錢包。
想確認什麼時候全部回來,看儀表板「放貸中部位」的到期欄位。

恢復:把 `paused` 改回 `false`(或從儀表板設定區關掉)。

若想連 GitHub Actions 都不跑,到 repo 的 Actions → Bitfinex Lending Bot → 右上 `⋯` → Disable workflow;
但這樣儀表板也會停止更新,通常沒必要。

## 歷史紀錄存檔

```
py export_history.py            # 匯出所有幣別
py export_history.py USD        # 只匯出指定幣別
```

會在 `history/` 產生四份 CSV(每個幣別一組),供日後回頭調策略:

| 檔案 | 內容 | 用途 |
|---|---|---|
| `*_funding_trades.csv` | 我們實際成交的每一筆放貸 | **調參主要依據**:實際拿到什麼利率 |
| `*_funding_offers.csv` | 掛單歷史,含被取消的 | 掛了什麼價 vs 成交了什麼價、成交率 |
| `*_funding_credits.csv` | 放貸部位,含開始與付息時間 | 資金實際被佔用多久 |
| `*_interest_payments.csv` | 每一筆入帳利息 | 真實收益,不受掛單策略推估影響 |

外加 `history/summary.json`:成交筆數、加權年化、利率區間、累計利息、掛單成交率。

**可重複執行**:會讀既有 CSV 以 ID 去重合併,所以之後定期跑就能持續累積,
不會因為 API 只回傳最近 N 筆而遺失更早的紀錄。建議恢復掛單前、或每隔一段時間跑一次。

> ⚠️ `history/` 會跟著 commit 進公開 repo(與儀表板同樣的公開選擇)。
> 若不想公開,把 `history/` 加進 `.gitignore` 並改用本機備份。

## 從儀表板修改參數

儀表板有「**參數設定**」區塊,可以用表單調整上表的欄位(利率欄位會即時換算成年化),
下方會同步產生新的 `config.json`。流程:

1. 改好欄位 → 按「**複製設定**」
2. 按「**在 GitHub 編輯**」開啟
   [config.json 編輯器](https://github.com/ChiJiun/bitfinex-lending-bot/edit/master/config.json)
3. 全選(Ctrl+A)貼上 → Commit
4. 機器人最多 15 分鐘後重讀設定並套用;執行 log 會顯示新參數的效果

表單只會動它認得的欄位,`period_rules` 與說明文字原樣保留。

### 為什麼設定不直接從網頁存檔

技術上做得到 —— 讓網頁拿一個 GitHub Token 直接 commit。**但這條路會打穿整個安全模型**:

- GitHub Token 要能改 `config.json`,就必須有 repo 的 `contents: write` 權限
- 有了那個權限,就能改 `bot.py`
- 而 `bot.py` 在 GitHub Actions 裡是帶著 `BFX_API_KEY` / `BFX_API_SECRET` 執行的

也就是說,**一個放在公開網頁上的 Token 若外流,等於交出你的 Bitfinex 放貸帳戶**。
GitHub 的細粒度 Token 也無法只授權單一檔案,擋不住這條路徑。

所以設計上刻意讓寫入權限**只走你自己的 GitHub 登入**:網頁負責把參數算好、驗證、產生 JSON,
真正的「存檔」由你在 GitHub 自己的介面按下 Commit。手機上同樣可用。

# 部署

## 1. 建立 Bitfinex API 金鑰

到 [Bitfinex API Keys](https://setting.bitfinex.com/api) 建立金鑰,權限**只勾**:

- Margin Funding → **Get funding statuses and info**(讀取)
- Margin Funding → **Offer, cancel and close funding**(下單)

⚠️ **不要**勾提領(Withdraw)或交易權限,被盜也偷不走錢。

## 2. 設定 Secrets

GitHub repo → Settings → Secrets and variables → Actions → New repository secret:

| 名稱 | 內容 |
|---|---|
| `BFX_API_KEY` | API Key |
| `BFX_API_SECRET` | API Secret |
| `DASHBOARD_PASSWORD` | 設定區密碼(看板本身不需要密碼,見下方) |

> ⚠️ 用 PowerShell 管線寫入 Secrets 會在值前面加上看不見的 BOM,導致 API 簽名失敗。
> 請直接在 GitHub 網頁貼上,或用 Bash。機器人本身已會自動清除金鑰開頭的 BOM 與空白。

## 3. 排程與長跑模式

[.github/workflows/lending-bot.yml](.github/workflows/lending-bot.yml) 每 15 分鐘**嘗試**啟動一個工作,
但真正的頻率不靠排程:每個工作在 `LOOP_MINUTES`(340)分鐘內每 60 秒檢查一次,
`concurrency` 保證同時只有一個工作在跑,前一個結束後排隊中的下一個立刻接手,所以掛單檢查幾乎不中斷。

為什麼不用排程本身:實測 GitHub 的 `*/15` 排程平均每 4 小時才真的跑一次(間隔 102~413 分鐘),
放貸回流後資金平均閒置 2 小時,是舊版年化偏低的主因。

- **公開 repo**:Actions 分鐘數無上限(長跑一天約用 1,440 分鐘)
- **私人 repo**:每月只有 2,000 免費分鐘,**不夠長跑**。請把 workflow 裡排程觸發的 `LOOP_MINUTES` 改成 `0`
  並接受排程的延遲,或改用自己的機器跑 `LOOP_MINUTES=1440 py bot.py`

手動觸發(workflow_dispatch)預設 `loop_minutes` 為 0,只跑一輪就結束,方便測試。

## 4. 測試

repo → Actions → Bitfinex Lending Bot → **Run workflow**,勾選 `dry_run` 先跑一次,
確認 log 顯示的掛單計畫合理,再取消勾選正式執行。

## 設定區的密碼

「參數設定」區塊要輸入密碼才會展開。比對方式:

1. workflow 用 Secret `DASHBOARD_PASSWORD` 算出 PBKDF2-HMAC-SHA256(300k 次 + 隨機 salt)雜湊
2. 雜湊隨 `data.json` 一起發佈(**密碼本身不會出現在任何檔案裡**)
3. 網頁把你輸入的密碼用同樣參數算一次,比對雜湊是否相同

解鎖狀態記在 sessionStorage,關閉分頁就失效。密碼存在本機的 `.dashboard_password`(未上傳)。

**這道鎖只是防手滑,不是安全機制**:

- 雜湊是公開的,所以 `DASHBOARD_PASSWORD` 必須夠長夠亂(預設是 20 字元隨機字串),
  否則會被離線暴力破解
- 檢查只在瀏覽器端執行,開 DevTools 就能繞過

但這不要緊 —— **設定頁本身不會、也不能改動 repo**。它只是產生一段 JSON 文字,
真正的寫入必須由你在 GitHub 按 Commit,那道關卡才是真正的權限控制。

## 改回加密看板

若之後想讓看板重新需要密碼才能看:把 `publish.py` 改回用 `DASHBOARD_PASSWORD`
做 AES-256-GCM 加密寫出 `data.enc`,前端改成解密後再渲染
(可從 git 歷史 `git log --oneline -- publish.py docs/index.html` 取回舊版)。
注意:**已經推上公開 repo 的明文資料會永久留在 git 歷史裡**,改回加密不會抹除。

# 本機測試

```
pip install -r requirements.txt
```

在專案目錄建立 `.env`(已被 .gitignore 排除):

```
BFX_API_KEY=你的key
BFX_API_SECRET=你的secret
DRY_RUN=1
```

執行 `py bot.py`。`DRY_RUN=1` 只會印出將執行的動作,不會真的下單或取消。

單元測試(純函式:定價、拆單、天期上限):

```
py -m pytest -q
```

回測(第一次會從公開 API 下載約 2 年的 15 分鐘 K 線並快取到 `.cache/`):

```
py backtest.py           # 舊版 vs 現行策略、不同執行頻率
py backtest.py --grid    # 加上參數掃描
```

長跑模式本機試跑(DRY_RUN 下只印動作):

```
DRY_RUN=1 LOOP_MINUTES=5 py bot.py
```
